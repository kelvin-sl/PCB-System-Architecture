# 舊板沿用與修改紀錄

## 先定位問題

以整體目標和固定條件開頭：哪些既有功能／區域需要保留，本輪是更新身份、連線還是位置。再說明目前卡在來源版本、元件對照、修改執行或驗證哪一步。只要求會改變下一步判斷的資料。

## 舊板與新設計對照

對照板檔、netlist內部產生版本、元件身份、device／footprint與逐腳net；記錄來源hash。資料夾名稱不是netlist新鮮度證據，BOARD未知不能自行補猜身份。

分別列出同身份沿用候選、連線表示差異待核對、改名候選、新增及移除。空net、No Connect與自動網名差異保留原值並列明正規化依據，不能直接視為等價或拓樸改變。同名footprint還需核對實際library幾何版本。

沿用候選不等於已保留placement，也不等於既有routing可沿用。記錄方案接受狀態與實際執行狀態。

## RefDes與匯入前後條件

先核對元件的可辨識特徵，建立舊名→新名表，檢查目標占用及改名順序。遇循環或重號，明確規劃可驗證的中間名稱，不能默默交換元件。API與匯入選項依當前版本核對，不把某次回傳值或選項當通用保證。

每次操作記錄以下欄位：

| 欄位 | 必填內容 |
|---|---|
| 身份與版本 | 板檔身份、腳本／mapping版本、run ID或可對應的執行時間 |
| 預期變更 | 本輪允許改哪些名稱／net／位置，目標後置條件 |
| 保持不變項 | 元件數、未受影響元件、封裝、XY、角度、板面、逐腳net等；依操作範圍選取 |
| 操作結果 | 原始API回傳、命令錯誤、實際已執行步驟與未執行步驟 |
| 新鮮讀回 | 操作後重新取得的物件與資料、報告時間／來源hash、預期與實際差異 |
| 保存狀態 | 是否儲存、是否部分修改、是否有可驗證的還原結果 |

批次改名要能識別完成到哪一筆；錯誤時先唯讀確認現況。改名後用映射對照原元件的不變項，不因ref改變就誤判為不同元件。netlist匯入前保存可還原副本與placement基準，匯入後分別核對保留、新增、移除及異常項。確認身份與所需後置條件前，不將後續匯入當作試錯手段。

## 保留出線區域

使用者要求某區域最小改動時，記錄其範圍、保留物件與可接受變更。只有component XY／pin net時，只能確認相應資料；保留trace、via、layer及拓樸需要對應routing資料與前後比較。位置相同、元件數相同都不能證明出線完整保留。

DXF底視圖、接合面及母板頂視圖先明確定義座標轉換；保留來源視角、旋轉、鏡像與Pin 1的核對依據。繪圖變換不直接當成實際元件角度。

## 修改record格式

將真實紀錄放專案目錄，逐次追加：時間／change ID、使用者需求、before、計畫action、已執行action、觀察到的after、證據版本、驗證界線、待辦、可萃取的通用方法。用superseded關係更新結論，不改寫舊嘗試為成功。

未解的API根因與未成功的修復只留問題紀錄。加入skill的內容應是已觀察支持的流程規則；移除板名、refdes、真實數值、路徑、報告和私有腳本。
